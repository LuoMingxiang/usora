# Usora — Architecture Proposal

> **Product:** Usora  
> **Positioning:** Personal Skill Hub for AI  
> **Tagline:** Turn practice into capability.

## 1. Product Positioning

Usora is an AI-independent, local-first plugin that helps users discover, generate, maintain, and reuse their own capabilities from everyday work with AI.

The core idea is not simply to manage `SKILL.md` files.

Usora turns real user experience into reusable AI capability:

```text
Experience
    ↓
Activity
    ↓
Pattern Discovery
    ↓
Candidate
    ↓
Skill
    ↓
Evaluation
    ↓
Evolution
```

The user may work with multiple AI systems, but they share one Personal Skill Hub.

## 2. Core Principle

### One User → One Skill Hub → Multiple AI → One Shared Capability Library

The Skill Hub belongs to the user, not to any particular AI.

Codex, Claude Code, CodeBuddy, WorkBuddy, Gemini, and future AI agents should be able to contribute to the same Hub.

## 3. Multi-AI Architecture

AI systems should not directly communicate with each other.

The plugin acts as the shared coordination layer:

```text
Codex
Claude Code
CodeBuddy
WorkBuddy
Gemini
    │
    ▼
Usora Plugin
    │
    ▼
Personal Skill Hub
```

Each AI interacts with Usora. The Hub becomes the shared source of truth.

## 4. Roles

### Worker

Any connected AI can act as a Worker.

Responsibilities:
- perform normal user work
- record useful Activities
- identify possible reusable patterns
- create Candidates
- submit observations

Workers cannot publish official Skills.

### Reviewer

A Reviewer can:
- inspect Candidates
- evaluate existing Skills
- identify duplication
- suggest improvements
- provide evaluation cases

A Reviewer does not necessarily have publishing authority.

### Maintainer

Each Personal Skill Hub has one configurable Primary Maintainer.

The Maintainer can:
- analyze Activities
- process Candidates
- merge or reject Candidates
- create and update Skills
- run evaluations
- publish Skills
- archive processed data
- maintain Skill versions

The Maintainer is a role, not a specific AI product.

For example:

```text
Primary Maintainer = Codex
```

can later become:

```text
Primary Maintainer = Claude Code
```

without changing the Hub architecture.

## 5. Permission Model

| Role | Activity | Candidate | Review | Skill Write | Publish |
|---|---:|---:|---:|---:|---:|
| Worker | Yes | Yes | Yes | No | No |
| Reviewer | Yes | Yes | Yes | No | No |
| Maintainer | Yes | Yes | Yes | Yes | Yes |

Key rule:

> Everyone can contribute; only the Maintainer can publish.

## 6. Activity

Activity is the lowest-level meaningful record in Usora.

An Activity represents useful work performed by the user with an AI.

Activity should not simply be a full conversation transcript. It should be normalized into structured information such as:

```json
{
  "id": "activity-xxx",
  "source": "codex",
  "session_id": "xxx",
  "project": "project-name",
  "timestamp": "2026-08-14T18:00:00",
  "task": "Solve a Vue memory leak",
  "context": "Memory increased after repeated page navigation",
  "approach": [
    "Inspect event listeners",
    "Inspect timers",
    "Inspect observers"
  ],
  "result": "Found an unremoved window listener",
  "technologies": [
    "Vue",
    "JavaScript"
  ],
  "outcome": "success"
}
```

The exact schema should remain extensible.

## 7. Activity Must Not Become Infinite Context

Activities may be stored long-term, but the entire historical Activity store must never be loaded into an AI context by default.

Usora should use incremental processing.

Typical lifecycle:

```text
NEW
 ↓
PROCESSED
 ↓
USED / ABSORBED
 ↓
ARCHIVED
```

The Maintainer should normally process:
- new Activities
- unprocessed Activities
- recent Activities
- Activities related to active Candidates or Skills

Historical Activities remain available without becoming part of every context window.

## 8. Activity Lifecycle and Cleanup

Usora should provide lifecycle management.

The system can identify:
- duplicate Activities
- low-value Activities
- Activities already absorbed into Skills
- Activities that can be compressed
- old Activities that are no longer useful

Possible actions:
- Keep
- Archive
- Compress
- Delete

The system may recommend cleanup automatically, but permanent deletion should be conservative.

The user should always be able to discover where data is stored and manage it themselves.

## 9. Candidate

A Candidate represents a pattern that an AI believes may deserve to become a reusable Skill.

Candidates may be generated by any connected AI.

Example:

```text
Claude Code
    ↓
observes repeated problem-solving pattern
    ↓
Candidate
```

A Candidate is not yet an official Skill.

Candidate evaluation can consider:
- frequency
- repetition across projects
- successful outcomes
- generality
- stability of the method
- reuse potential
- similarity to existing Skills

The goal is to avoid generating Skills from one-off events.

## 10. Skill Lifecycle

```text
Candidate
    ↓
Draft
    ↓
Evaluation
    ↓
Published
    ↓
Updated
    ↓
Deprecated / Archived
```

A Skill is a maintained capability asset, not merely a generated document.

## 11. Skill Format

Skills should use an AI-agent-compatible format.

A minimal Skill may look like:

```text
skill-name/
└── SKILL.md
```

A more complete Skill may contain:

```text
skill-name/
├── SKILL.md
├── references/
├── scripts/
├── tests/
└── examples/
```

Skills should remain as AI-independent as reasonably possible.

## 12. Skill Evaluation

Before publishing or updating a Skill, the Maintainer should evaluate it against useful historical cases when possible.

```text
Skill Draft
    ↓
Historical Cases
    ↓
Evaluation
    ↓
PASS / FAIL
```

Evaluation may consider:
- correctness
- success rate
- missing steps
- false positives
- required human intervention
- improvement over existing Skills

## 13. Skill Evolution

Skills should continuously evolve.

Example:

```text
vue-memory-leak-audit v1.0
```

After repeated usage, new Activities may reveal an additional pattern.

The system can produce:

```text
Improvement Candidate
    ↓
Maintainer
    ↓
Skill v1.1
    ↓
Evaluation
    ↓
Publish
```

Thus Usora is a continuous capability-evolution system.

## 14. Sync

All connected AIs may expose the same conceptual operation:

```text
skillhub sync
```

But the result depends on the current AI's role.

### Worker / Reviewer

```text
Collect Activity
    ↓
Analyze
    ↓
Generate Candidate
    ↓
Submit
```

It does not publish official Skills.

### Maintainer

```text
Collect Activity
    ↓
Analyze
    ↓
Process Candidates
    ↓
Merge / Reject
    ↓
Generate Skill
    ↓
Evaluate
    ↓
Publish
    ↓
Archive processed data
```

Therefore:

> Sync is a state-progression operation, not merely file synchronization.

## 15. Trigger Strategy

The underlying pipeline should be independent of its trigger.

Supported modes:

### Manual

The user explicitly asks the AI to sync:

> “Sync my Skill Hub.”

or:

```text
skillhub sync
```

### Automatic

Users may configure automatic triggers such as:
- daily
- weekly
- after session
- after task
- future event-based triggers

The pipeline remains the same regardless of how it is triggered.

## 16. Default Automation Policy

The product should be automation-first.

Default behavior:

```text
Activity
    ↓
Automatic Discovery
    ↓
Candidate
    ↓
Maintainer Generation
    ↓
Evaluation
    ↓
Automatic Publish
```

Therefore:

> **Default: automatically generate and publish useful Skills.**

The behavior must be configurable.

Possible policies:

```text
auto_publish
manual_approval
auto_generate_manual_publish
```

## 17. User Interaction

The MVP should not require a graphical interface.

Usora should work inside the user's existing AI environment:
- Codex Desktop
- Claude Code
- CodeBuddy
- WorkBuddy
- other supported AI agents

The user should not need to open a separate Skill Hub application.

## 18. Natural Language First

Users should be able to say:

> Initialize my Skill Hub.

The AI can guide them through:

```text
Initialize
 ↓
Choose storage
 ↓
Choose Maintainer
 ↓
Choose automation policy
 ↓
Complete
```

Other examples:

> Sync my Skill Hub.

> Show me the Skills created recently.

> Clean up Activities that are no longer useful.

> Change my Maintainer to Claude Code.

Natural language should map to the same underlying Core Operations used by the CLI.

## 19. CLI

A CLI may be provided for advanced users and automation:

```text
skillhub init
skillhub sync
skillhub status
skillhub candidates
skillhub skills
skillhub review
skillhub publish
skillhub clean
skillhub doctor
skillhub config
```

CLI is an interface, not the core architecture.

## 20. Local-First Storage

The first implementation should be local-first and Git-friendly.

Possible default:

```text
~/.usora/
```

or a user-selected directory.

Example:

```text
.usora/
├── config.json
├── activities/
├── candidates/
├── skills/
├── reviews/
├── evaluations/
└── state/
```

The repository may be initialized as a Git repository.

Benefits:
- version control
- diff
- rollback
- backup
- history
- portability

## 21. Remote Storage

GitHub, GitLab, Gitea, or other remote repositories should not be required for the MVP.

Architecture:

```text
Local
  ↓
Git
  ↓
Optional Remote
```

Remote synchronization can be added later.

## 22. Plugin Architecture

The plugin is the integration and coordination layer.

Responsibilities include:
- Activity collection
- Activity normalization
- local storage
- role and permission handling
- Candidate management
- Skill management
- event handling
- AI adapter integration
- lifecycle management

The plugin must not assume direct AI-to-AI communication.

## 23. AI Adapters

Each supported AI environment should have an adapter.

Example:

```text
adapters/
├── codex/
├── claude-code/
├── codebuddy/
├── workbuddy/
└── gemini/
```

Adapters should primarily translate:

```text
AI Session
    ↓
Normalized Activity
```

They should not contain the core Skill business logic.

The Core should not need to know how a particular AI works.

## 24. Maintainer Configuration

The user can configure the Primary Maintainer.

Natural language:

> Make Codex my Skill Hub Maintainer.

or:

```text
skillhub config maintainer codex
```

Changing the Maintainer should not change the data model.

## 25. Maintainer Is Not the Activity Source

The Maintainer may also act as a normal Worker.

For example:

```text
Codex
 ├── Worker → creates Activity
 └── Maintainer → processes Activity
```

Role and data source are separate concepts.

## 26. Event Model

Important events may include:

```text
ActivityCreated
CandidateCreated
CandidateUpdated
ReviewSubmitted
SkillDraftCreated
SkillEvaluationStarted
SkillEvaluationCompleted
SkillPublished
SkillUpdated
ActivityArchived
```

The event model should make the system extensible and allow future automation.

## 27. Core Pipeline

The central Usora pipeline is:

```text
AI Work
   ↓
Activity
   ↓
Activity Normalization
   ↓
Pattern Discovery
   ↓
Candidate
   ↓
Review
   ↓
Maintainer
   ↓
Skill Draft
   ↓
Evaluation
   ↓
Publish
   ↓
Skill
   ↓
Future AI Work
   ↓
New Activity
   ↓
Evolution
```

This creates a continuous loop:

```text
Experience
    ↓
Activity
    ↓
Knowledge / Pattern
    ↓
Skill
    ↓
Reuse
    ↓
New Experience
```

## 28. MVP Scope

### P0

1. Skill Hub initialization
2. Local storage
3. Git support
4. AI Adapter abstraction
5. Activity schema
6. Activity collection
7. Candidate generation
8. Maintainer configuration
9. Skill generation
10. Skill evaluation
11. Skill versioning
12. Skill publishing
13. Basic archive / cleanup
14. Natural language interaction
15. CLI fallback

## 29. Explicit Non-Goals for MVP

Do not build initially:
- Web Dashboard
- graphical UI
- Skill Marketplace
- public community
- team collaboration
- payment
- public Skill ranking
- complex cloud backend
- multi-Hub architecture
- direct AI-to-AI communication
- mandatory online service

## 30. Future Expansion

The Personal Skill Hub may eventually connect to broader registries:

```text
Personal Skill Hub
        ↓
Team Skill Registry
        ↓
Enterprise Skill Registry
        ↓
Community Registry
        ↓
Skill Marketplace
```

Marketplace and community distribution are future layers, not the core Personal Skill Hub.

## 31. Product Value

Usora is not simply:

> “a manager for SKILL.md files.”

Its core value is:

> **Turn the user's accumulated experience into reusable AI capability.**

Traditional workflow:

```text
Person solves problem
    ↓
Experience remains mostly in memory
    ↓
Experience is gradually forgotten
```

Usora:

```text
Person + AI solve problem
    ↓
Activity
    ↓
Pattern Discovery
    ↓
Skill
    ↓
Future AI reuses it
```

## 32. Final Product Definition

> **Usora is an AI-independent, local-first plugin that lets multiple AI agents learn from a user's real-world work, automatically discover reusable patterns, and turn those experiences into evolving personal Skills.**

Core principles:

> **One User → One Skill Hub → Multiple AI → One Shared Capability Library**

> **Everyone can contribute; only the Maintainer can publish.**

> **Automatic by default, configurable by the user.**

> **Local-first, Git-friendly, AI-independent.**

> **Natural language first, CLI second, no GUI required.**

> **Activity → Candidate → Skill → Evaluation → Evolution.**

## 33. Architectural Boundary

Usora should not become another AI.

It should not become a tool tightly coupled to Codex.

It should be infrastructure that allows multiple AI agents to collaborate around one user's evolving capability library.

Codex may be the Maintainer.

Claude Code may become the Maintainer.

Other AI agents may become the Maintainer later.

But the Skills belong to:

```text
User's Personal Skill Hub
```

not to:

```text
Codex
Claude
Gemini
CodeBuddy
WorkBuddy
```

This boundary should remain fundamental to the architecture.
