# Plugin Platform Notes

Usora is a TypeScript-first multi-plugin marketplace monorepo. Each plugin owns one canonical manifest, one TypeScript source tree, one built runtime, and zero hand-maintained generated JavaScript.

## Distribution Model

Usora has three layers:

| Layer               | Purpose                                | Contains                                                               | Must not contain                                              |
| :------------------ | :------------------------------------- | :--------------------------------------------------------------------- | :------------------------------------------------------------ |
| Source branch       | Contributor workflow                   | `plugins/*/src/**/*.ts`, tests, packages, tooling                      | committed `dist/`                                             |
| Distribution tree   | Git marketplace payload                | `marketplace.json`, `plugins/*/dist`, runtime metadata, skills, assets | `src/`, tests, `packages/`, `tooling/`, `.ts`, `.mjs`, `.map` |
| Per-plugin artifact | Single-plugin download/release payload | one packaged plugin runtime                                            | any workspace-only files                                      |

Published marketplace installs should resolve the generated `marketplace` branch or an equivalent distribution export, never the source branch.

## Canonical Plugin Layout

Every plugin follows the same minimum layout:

```text
plugins/<name>/
├── src/
│   └── cli/mcp.ts
├── skills/
├── hooks/
├── assets/
├── .codex-plugin/
├── .codebuddy-plugin/
├── .mcp.json
├── plugin.json
├── package.json
└── tsconfig.json
```

`src/**/*.ts` is the only business source. `dist/*.js` is generated by the build and is the only runtime loaded by hosts.

## Manifest and Host Metadata

Edit `plugins/<name>/plugin.json` first. This file is the source of truth for:

- plugin identity: `name`, `displayName`, `version`, `description`
- runtime contract: `runtime.node`, `entrypoints`
- portable capabilities: `skills`, `mcpServers`, host-facing interface metadata

Current runtime entrypoints must point to built JavaScript, for example:

```json
{
  "schemaVersion": 1,
  "name": "foundry",
  "runtime": { "node": ">=20" },
  "entrypoints": {
    "mcp": "dist/mcp.js",
    "sessionHook": "dist/session-hook.js"
  }
}
```

Then sync generated marketplace metadata:

```powershell
bun run sync
bun run doctor
```

Generated host metadata should stay generated. Only add host-specific fields when they cannot be represented in the root manifest.

## Build, Test, and Package

Contributor loop:

```powershell
bun run check
bun run build
bun run package:check
bun run runtime:check
```

Useful single-plugin commands:

```powershell
bun run build:foundry
bun run package:foundry
bun run release:plan
bun run release:plugins
```

`bun run check` is the production gate. It covers formatting, linting, typecheck, build, package validation, clean runtime validation, marketplace validation, tests, and plugin validation.

## Scaffold a New Plugin

Create a new plugin with:

```powershell
bun run plugin:create <name>
```

The scaffold creates:

- `plugin.json` with schema, version, node runtime, and `dist/mcp.js` entrypoint
- `src/cli/mcp.ts`
- `.mcp.json`
- `.codex-plugin/plugin.json`
- `.codebuddy-plugin/plugin.json`
- `.codebuddy-plugin/mcp.json`
- `hooks/*.json`
- `package.json`
- `tsconfig.json`

After scaffolding:

```powershell
bun run sync
bun run build
bun run test
```

New plugins enter discovery, affected analysis, CI matrices, package validation, and release planning by adding a valid `plugins/<name>/plugin.json`. No Foundry allow-list should be edited.

## Release and Distribution

Usora supports two production distribution modes:

1. Git marketplace distribution: `bun run marketplace:build` prepares the clean marketplace tree, and `bun run release:marketplace` publishes the generated `marketplace` branch.
2. Per-plugin artifact distribution: `bun run package` creates `artifacts/usora-<plugin>-<version>.zip` plus checksum, and `bun run release:plugins` turns releasable plugins into tagged GitHub releases.

Versioning is per plugin. A plugin tag, manifest version, and packaged artifact version must match.

## Minimal Host Adapter Rules

When adding a new host adapter:

- keep `plugins/<name>/plugin.json` canonical
- point runtime metadata only at `dist/*.js`
- use host-local variables only for host path resolution, such as `${CODEBUDDY_PLUGIN_ROOT}`
- keep host adapters thin: path resolution, host metadata shape, and optional host-only prompts
- do not move business logic from `src/` into host metadata or wrappers

If a host needs a different marketplace file or MCP config shape, generate it from the canonical manifest instead of forking plugin behavior.
